# DocDiffGuard

多文档差异对比与角色混淆治理器。

给定两份文档：**BASE**（润色版，只读基准）和 **REF**（转录版，参考，不允许编造内容），找出 BASE 中有、但 REF 中没有或语义不同的内容，汇总成“转录版需要修改的点”清单。每条结论都可以溯源到原文。

## 设计原则

- **角色显式绑定**：通过 `--base` 和 `--ref` 指定角色，不依赖参数顺序猜测。
- **单次任务只处理两个文件**：不引入历史文件，避免污染。
- **先解析、分段、对齐，再判断**：判断只在对齐结果上进行。
- **规则优先，LLM 可选**：所有结论先由规则给出。LLM 只对 `fuzzy` 候选做补充判断；没有 API 或调用失败时，自动降级为规则判断。
- **引用必须可校验**：输出的原文片段必须能在对应文档中找到，找不到就丢弃并记录。

## 快速开始

环境：Python 3.11+，推荐使用项目内的虚拟环境 `.venv`。

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

命令行：

```bash
python aligner.py --base samples/base_test.docx --ref samples/ref_test.txt > result.json
python report.py result.json > report.md
```

LLM 判断（可选，需要设置环境变量 `ANTHROPIC_API_KEY`，没有设置时自动降级为规则）：

```bash
python judge.py --base samples/base_test.docx --ref samples/ref_test.txt
```

网页界面：

```bash
streamlit run app.py
```

评测：

```bash
python eval.py
python eval_llm.py
```

## 处理流程

| 步骤 | 文件 | 做什么 |
|---|---|---|
| 1. 读取 | `reader.py` | 读取 `.txt` 或 `.docx`，切分段落，编号 P001、R001 |
| 2. 绑定 | `binder.py` | 检查文件存在、两个文件不是同一个、内容非空，返回 `DocPair` |
| 3. 对齐 | `aligner.py` | 用 `difflib` 计算相似度，每个 BASE 段落取最佳匹配 |
| 4. 分类 | `aligner.py` | 见下文“分类规则” |
| 5. 结构化 | `models.py` | 用 Pydantic 定义 `AlignmentResult`，校验字段类型和取值范围 |
| 6. 校验 | `aligner.py` | `validate_results`：引用必须能在原文中找到，否则丢弃 |
| 7. 报告 | `report.py` | 按 `missing` 和 `modified` 分组，生成修改清单 |
| 8. 判断（可选） | `judge.py` | 只对 `fuzzy` 候选调用 LLM 判断，输出 JSON 并校验证据；API 失败或输出无法解析时降级为规则判断 |

## 分类规则

1. 计算相似度前，先去掉标点和空白。
2. 相似度分数划分：
   - 高于 0.92，且没有实质性增删，判为 `same`（一致）；
   - 0.75 到 0.92，判为 `fuzzy`（报告中称为“modified”，需要人工复核）；
   - 低于 0.75，判为 `missing`（REF 中没有对应内容）。
3. 只要有实质性的文字增删，即使分数高于 0.92，也不能判为 `same`。
4. `fuzzy` 候选可以再交给 LLM 判断。LLM 的输出必须符合 `JudgeVerdict` 结构，`evidence` 必须能在 BASE 原文中找到。

阈值 0.92 和 0.75 是人工设定的，没有用真实文档数据调校。

## 评测

评测用例保存在 `eval_cases.json`，共 20 条，覆盖：
- 三种标签（`same`、`fuzzy`、`missing`）；
- 标点差异、删减、数字变化；
- 多段落、段落顺序对调、REF 有额外内容、REF 缺少内容。

规则流程的指标（在这 20 条自建用例上）：

| 指标 | 结果 |
|---|---|
| 差异检测：精确率 / 召回率 / F1 | 1.000 / 1.000 / 1.000 |
| 顺序正确率（17 项检查） | 1.000 |
| 引用准确率 / 幻觉率 | 1.000 / 0.000 |
| 格式合规率 | 1.000 |
| 角色混淆率 | 0.000 |

**注意**：满分只说明规则在自建用例上正确，不代表真实文档上的准确率。引用准确率、幻觉率、格式合规率和角色混淆率在纯规则流程中本来就不会出错，它们是守门指标，主要用于发现 LLM 判断引入的问题。

LLM 判断的评测（`python eval_llm.py`，共 17 个段落，约 17 次 API 调用）：
- `fuzzy`：4 条，与期望一致 4 条，降级 0 条；
- `same`：13 条，与期望一致 13 条，降级 0 条。

这是自建用例上的结果，样本量很小，不代表真实文档上的准确率。统计时，降级的结果不计入 LLM 的正确结果。

### 真实文档验证（一对文档，结果有限）

这是本项目唯一一次用真实文档做的验证，只做过一次。使用一份个人文档的两个版本：B1（BASE，润色版，57 段）和 B2（REF，转录版，56 段）。

**验证过程中出过问题**：B2 在转录时被 Kimi（一个 AI 工具）加入了未经授权的内容，并且使用了 B0（原始版本）的数据，我没有要求它这么做。这些内容一度被当作验证结果的一部分。因此下面的数字只说明工具对这份 B2 的反应，不代表对干净文档的准确率。为此，项目新增了 `check_additions.py`，用来检查目标文档里是否有来源之外的句子。

**这次验证的原始文档没有公开。**

- **规则流程**：52 段 `same`，4 段 `fuzzy`，1 段 `missing`。
- **标注**：草稿标签由作者通读全文给出，未经第二人确认。以此计算，默认阈值（0.92 / 0.75）下精确率 0.80、召回率 1.00、F1 0.889；三类完全一致 55/57。在 0.85–0.95 与 0.70–0.80 的范围内结果不变。
- **已知错误**：
  - P030：背景段被改写并扩写，规则判为 `missing`，实际应为 `fuzzy`。
  - P031：内容完整包含在 B2 的合并段落中，规则判为 `fuzzy`，实际应为 `same`。这两例都是段落切分不一致导致的，一对一的最佳匹配对此无效。
- **LLM 判断**：对 4 个 `fuzzy` 段落调用，全部成功（降级 0 次），3 段的 `evidence` 未能逐字在 BASE 中找到，被证据检查丢弃。P031 被判为 `modified`，与草稿标签不一致，原因同上。
- **来源检查**（`check_additions.py`）：B2 中有 5 句原文来自 B0，不在 B1 中；另有 1 句在 B0 和 B1 中都找不到，需要人工确认。

## 失败模式与已知限制

- **小幅删减被误判为一致**：删掉 5 个字后分数仍高于 0.92。已修复：有实质性增删时不再判为 `same`。这一问题由用例 C005 发现。
- **短句的标点差异拉低分数**：例如“报告！”和“报告。”只差一个字符，短句的分数会低于 0.92，被误判为 `fuzzy`。已修复：计算前去掉标点。这一问题由用例 C008 发现。
- **基于字符，不理解语义**：同义改写可能被判为 `missing`，也可能被判为 `fuzzy`。
- **最佳匹配可能重复**：两个 BASE 段落可能指向同一个 REF 段落。例如 P002 和 P003 本身很相似，在完整复制的 REF 中，P003 与 R002 的分数是 0.903。
- **守门指标没有实际检测力**：纯规则流程里这些指标恒为 100%。
- **LLM 输出可能被截断**：模型的思考内容占用 `max_tokens`，额度不足时文字部分为空或不完整。已通过把 `max_tokens` 提高到 4096 解决；换模型或换文档时可能需要重新调整。
- **LLM 输出格式不稳定**：模型有时会用代码块包住 JSON。已通过只提取第一个 `{` 到最后一个 `}` 之间的内容解决。
- **临时文件未清理**：网页端每次刷新都会在系统临时目录生成新文件。
- **格式支持有限**：只支持 `.txt` 和 `.docx`，不支持 `.pdf`。

## 复盘

- **每一步都用真实运行的输出验证**，而不是只看代码。多次出现“看起来对、实际没运行”的情况，原因包括：在错误的终端窗口里运行、文件没有保存、文件位置不对。
- **测试驱动规则修复**：C005 和 C008 的失败直接导致了规则修改。修复时没有改动期望值，而是改进规则。
- **统计要排除降级结果**：一次 LLM 调用失败后降级为规则，结果可能恰好与期望一致，如果计入 LLM 的正确率，会高估 LLM 的表现。这一点是在评测时发现的。
- **全部通过不等于准确**：20 条自建用例是我们自己设计的，而且是在失败后逐步调整的，可能存在偏差。下一步应该用真实文档做测试。
- **先验证再接入**：先用不需要密钥的降级部分搭好接口，再接入真实调用，每一步都用真实输出确认。

## 目录结构

```
docdiffguard/
├── reader.py         读取 .txt / .docx，切分段落
├── binder.py         绑定 BASE 和 REF，检查输入
├── aligner.py        相似度计算、分类、结果构建与校验
├── models.py         Pydantic 结构化结果（AlignmentResult、JudgeVerdict）
├── report.py         生成修改清单
├── check_additions.py 列出目标文档中在所有来源里都找不到原文的句子
├── judge.py          LLM 判断（含规则降级）与证据检查
├── eval.py           评测脚本
├── eval_llm.py       LLM 判断的评测脚本
├── eval_cases.json   20 条自建评测用例
├── app.py            Streamlit 界面
├── requirements.txt  依赖
└── samples/          测试用的 BASE 和 REF 文件
```
